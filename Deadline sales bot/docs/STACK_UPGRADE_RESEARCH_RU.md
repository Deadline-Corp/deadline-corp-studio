## Слой 1 — WhatsApp-коннектор (замена WAHA)

### Как сейчас
- `channels/waha.py` → self-hosted **WAHA** (devlikeapro/waha), движок **NOWEB** = обёртка над Baileys, на Contabo VPS (Docker). Номер по QR как linked-device, неофициально, $0, номер остаётся в телефоне.
- **Боли (из кода и памяти проекта):**
  1. Отправка рекламным лидам на `@lid` через NOWEB застревает «Waiting for this message»; приватным лидам Meta не отдаёт номер (`pn:null`).
  2. NOWEB отдаёт media-URL на `localhost:3000` → переписываем хост вручную (`_fix_media_url`).
  3. History sync требует флагов `NOWEB_STORE_ENABLED/FULLSYNC`, был нестабилен.
  4. Нет обработки удалений/редактирований.
  5. Риск бана рабочего номера.
  6. Мультисессия (каждый тенант — свой номер) на WAHA Core невозможна (Core = 1 сессия).

### Рекомендация (поэтапно)

**Шаг A — сразу, $0, почти без риска: WAHA NOWEB → GOWS.**
GOWS = движок WAHA на базе whatsmeow (Go). **Доступен в БЕСПЛАТНОЙ WAHA Core** (подтверждено: Docker-команда с `WHATSAPP_DEFAULT_ENGINE=GOWS` без `-plus`) — НЕ требует платного Plus. Переключается **одной env-переменной**. Ваш `channels/waha.py` НЕ меняется (тот же REST API). ⚠️ при смене движка номер один раз пере-сканирует QR (другой стор сессии). Чинит сразу 3 боли:
- media-URL приходит корректным внешним адресом — хак `_fix_media_url` больше не нужен;
- history sync через `WAHA_GOWS_DEVICE_HISTORY_SYNC_FULL_SYNC_DAYS_LIMIT=30` — стабильнее флага FULLSYNC;
- `message.revoked` + `message.edited` работают нативно.
- Меньше CPU/RAM (нет Chromium). Отправка на `@lid` через whatsmeow напрямую — без застревания «Waiting for this message».
> Скрытый номер рекламного лида (`pn:null`) GOWS **не решает** — это политика Meta, одинаково у всех.

**Шаг B — для мультитенанта/будущей официальной миграции: Evolution API.**
- мультисессия (`/instance/create`) **бесплатно** (важно для self-service подключения номера каждым клиентом);
- `MESSAGES_DELETE` + `MESSAGES_UPDATE` из коробки;
- **нативная интеграция с Chatwoot** (см. слой 2) — связка под общий инбокс;
- **официальный Meta Cloud API как drop-in движок** в той же кодовой базе → когда дойдёте до оплат и официального API, миграция = смена движка, не переписывание.
- Минусы честно: та же `@lid`/Baileys-проблема (open meta-issue #1872), нужен Redis+Postgres, в проде ловили дисконнекты, релизов нет ~полгода. Поднять на VPS рядом с WAHA как PoC, померить стабильность на тест-номере.

### СЕЙЧАС → СТАНЕТ (пример: рекламный @lid-лид «Интересует»)
- **NOWEB:** webhook `from:"187…@lid"` → резолв LID API (часто `pn:null`) → ответ застревает «Waiting for this message» → media-URL `localhost:3000` переписываем вручную.
- **GOWS:** тот же webhook → media-URL уже корректный → ответ на `@lid` уходит через whatsmeow без застревания → удаление/редактирование ловится нативно. Скрытый номер по-прежнему недоступен (Meta).

### Честно про бан и официальный API
Все варианты — реверс WhatsApp Web, нарушение ToS, риск бана одинаковый (баны волнами, одиночный номер с человекоподобными паузами — риск ниже). Официальный Cloud API станет **неизбежен**: шаблонные/outbound-сообщения, платёжные уведомления (ваш этап оплат), верификация бизнеса, масштаб >10 номеров. Поэтому **Evolution API стратегически удобен** — даёт бесплатный неофициальный сейчас и официальный drop-in потом.

## Слой 2 — Все каналы в одно окно (Chatwoot)

### Как сейчас
Каждый адаптер (telegram/whatsapp/waha/greenapi/messenger/instagram) нормализует входящие в одну таблицу `conversations` → своя React-панель «Переписки» + воронка-канбан + задачи + редактор «мозга». Омниканальность уже есть, но самописная: нет полноценного шаред-инбокса (назначение операторов, метки, SLA, командная работа), нет мобильного приложения, каждый коннектор пишем сами.

### Chatwoot (chatwoot/chatwoot, MIT, 32.6k★, v4.15.1 от 17.06.2026)
- Каналы из коробки: WhatsApp (офиц. Cloud API **или** WAHA/Evolution), Telegram, Instagram, Facebook, web-виджет, email, API-канал, SMS, Line.
- **Agent Bot API** — ровно ваш сценарий: внешний бот получает сообщения по webhook, отвечает через REST. Нужен оператор → бот ставит `status:open`, диалог падает в очередь операторов; оператор перехватывает, назначает, ставит метку; вернуть боту → `status:pending`. Двунаправленный handoff с сохранением контекста.
- Мобильное приложение оператора (iOS/Android), метки, заметки, canned-ответы, авто-роутинг, базовая аналитика — бесплатно в CE.
- Нативная связка **WAHA↔Chatwoot** и **Evolution↔Chatwoot** — WhatsApp заводится без своего коннектора.

### Архитектура «Chatwoot как инбокс + ваш мозг как Agent Bot»
```
Каналы → WAHA/Evolution → Chatwoot (инбокс, операторы, UI) → webhook → FastAPI-«мозг»
   (логика/LLM/CRM) → Chatwoot API → ответ клиенту;  нужен человек → status:open
```
Стандартная задокументированная схема (есть офиц. демо `chatwoot/rasa-agent-bot-demo`). **«Мозг» не выбрасывается** — Chatwoot добавляется слоем поверх.

### СЕЙЧАС → СТАНЕТ
- **Сейчас:** лид в WhatsApp → WAHA → `conversations` → React-панель. Назначение/метки/SLA/мобайл — нет или самопис.
- **Станет:** лид → WAHA → Chatwoot (`pending`) → ваш бот по webhook отвечает через Chatwoot API → если нужен человек, бот ставит `open` → оператор в вебе/мобайле видит весь контекст, берёт, ставит метку «горячий», отвечает; вернуть боту → `pending`.
- **Выигрыш:** готовые коннекторы, командная работа, метки/фильтры/поиск, мобайл-апп, один UI на все каналы.
- **Цена:** тяжёлый (Rails+Sidekiq+Postgres+Redis, ~4 ГБ RAM, +$20-40-мес); **два источника правды** (история в Chatwoot + контекст в вашем Postgres — синхронизировать webhook'ами); конфиг раздваивается (логика бота — в вашей админке, маршрутизация — в Chatwoot).
- **Вердикт:** окупается от **3+ операторов** или когда нужен мобайл/командная работа. Для 1-2 человек — самописной панели хватает, можно взять только идеи/коннекторы.

## Слой 3 — «Мозг» диалога (Dify + LangGraph)

### Как сейчас
На каждый ход: **один** вызов LLM (OpenRouter llama-3.3-70b / Gemini / Groq) + pgvector/bge-m3 RAG (`db.vector.similarity_search`) + промпт в коде (`prompts.build_chat_prompt`) + few-shot + история. Вся детерминистика и постобработка — **кодом** (`reply_polish.py`): слоты созвона, детект alt-канала, дедуп follow-up, обрезка артефактов — потому что llama ненадёжно слушается prose-правил. Свои режимы HITL (наблюдение/черновик/автономно) — самописно.

### Dify (langgenius/dify, Apache-2.0 +огранич., ~146k★)
LLMOps-платформа (Docker): визуальный конструктор воркфлоу, RAG с UI управления документами (загрузка→чанкинг→эмбеддинг), Prompt-IDE с версиями и A/B, нода Human-Input (HITL, с v1.13 апр-2026), наблюдаемость токенов/латентности, REST API чтобы дёргать как сервис.

**Подсервис без переписывания:** FastAPI дёргает `POST /v1/chat-messages` Dify вместо прямого OpenRouter; промпты и RAG живут в Dify UI; ваши код-гарды работают **поверх** ответа Dify — не трогаются.

**СЕЙЧАС → СТАНЕТ (клиент просит поправить ответ про цены / добавить документ в базу):**
- Сейчас: правка `prompts.py` / эмбеддинг-скрипт → коммит → деплой → QA → прод. Нет версий промпта, нет A/B.
- С Dify: не-разработчик правит промпт в UI (история версий, тест на golden-set, A/B) **без деплоя**; менеджер грузит документ в Knowledge Base через UI — бот сразу использует. Критично для вашего мультитенанта, где клиенты сами настраивают бота.
- Чего Dify НЕ заменяет: произвольный Python поверх ответа. Слоты/дедуп/детект-канала/обрезку — держим кодом как и сейчас.
- ⚠️ Лиценз-нюанс: мультитенантный SaaS на одном Dify формально требует коммерч. лицензии LangGenius; либо отдельный self-hosted Dify на клиента. Уточнить до внедрения.

### LangGraph (langchain-ai/langgraph, ядро MIT, ~18k★, v1.2.5 от 12.06.2026)
Python-библиотека: диалог как **граф состояний** — узлы, рёбра, общий typed-state, checkpointing, `interrupt()` для HITL. Не сервис — импорт в ваш же Python.

**СЕЙЧАС → СТАНЕТ (воронка бронирования как граф):**
```
qualify_lead ─[нет]→ soft_close
            └[да]→ offer_slot → interrupt() [админ видит черновик, жмёт ✅]
                      → send_to_lead → await_confirmation
                            ├[подтвердил]→ book_slot → HubSpot → END
                            ├[другое время]→ offer_slot (цикл)
                            └[отказ]→ escalate (человек)
```
- Сейчас: «воронка» = `if/elif` поверх одного LLM-вызова, который сам угадывает этап из контекста → отсюда ненадёжность, лечится `reply_polish`-костылями.
- Станет: каждый узел — одна задача, рёбра — явный код (не промпт); checkpointing в Postgres (упал процесс — граф продолжит с того же узла); LLM не «путается» в этапах.
- **Цена:** это **переписать поток** диалога (узлы/рёбра/state), недели на живом проде. Ядро MIT (только `langgraph up`-сервер — ELv2, вам не нужен — вы пишете FastAPI сами).

### Альтернативы (кратко)
**Flowise** (Apache-2.0, 53k★) — проще Dify, RAG-UI без enterprise/HITL. **n8n** (fair-code, 160k★) — оркестратор автоматизаций «вокруг» бота (follow-up, уведомления, синк HubSpot), не замена мозга. **Langflow** (MIT, 149k★) — Python-нативный аналог Dify. **Rasa** — устаревшая для нового LLM-проекта парадигма, OSS в maintenance — **не брать**.

### Вердикт по мозгу
- **Dify** — реальный «подсервис без переписывания» → делать первым (PoC на одном тенанте), минимум риска для прода, максимум пользы (правка промптов/базы без деплоя).
- **LangGraph** — фаза 2, это рефактор потока, когда воронка созреет.
- Код-гарды (детерминистика) остаются **всегда**, чем бы ни был мозг.

## Слой 4 — Воронка / задачник (НЕ мигрировать, перенять 7 паттернов)

### Как сейчас
Самописные стадии воронки + канбан + задачи + автоматизации на смену стадии + зеркало в HubSpot (контакт/сделка/стадия/задача 1:1 через очередь `crm_events`).

### Кандидаты (смотреть как идеи, не как замену)
Twenty (~50k★, AGPL), EspoCRM (~2.9k★, AGPL), Frappe CRM (~2.8k★, AGPL), Odoo CE (~52k★, LGPL). Все AGPL/LGPL → деплой как сервис = открыть код или купить Enterprise. **Мигрировать не нужно** — у вас уже своя ниша-воронка + HubSpot-зеркало.

### 7 паттернов для переноса в свою Postgres-модель
1. **Стадия с вероятностью** (`win_probability`) → взвешенный forecast `SUM(amount*prob/100)`.
2. **Причина проигрыша** (`lost_reason` enum, обязат. при CLOSED_LOST) → аналитика «где теряем».
3. **Activity timeline** (append-only `deal_events(actor,type,payload,ts)`) → новый оператор видит контекст.
4. **SLA / протухание лида** (`last_activity_at` + фоновый job → алерт оператору, если лид молчит N дней).
5. **Назначение/роутинг** (`owner_id` + `assignment_rules`: round-robin / by-load) → лиды не теряются.
6. **Кастомные поля / мультипайплайны** (`pipelines`+`pipeline_stages`, JSONB extra) → разные воронки под тип сделки.
7. **Конверсионная аналитика по стадиям** (`stage_transitions` → конверсия и median-time-in-stage) → видно узкое горло.

Все 7 — эволюция вашей модели (таблицы/поля/джобы/дашборды), ортогональны HubSpot-зеркалу.

## Рекомендуемая последовательность (от дешёвого/безопасного к крупному)

1. **WAHA NOWEB → GOWS** — 1 env-переменная, $0, чинит media/history/удаления. Проверить на запасном номере. **Наивысший ROI.**
2. **PoC Evolution API** на VPS (тест-номер) — мультисессия + нативный Chatwoot + drop-in официальный API. Померить стабильность.
3. **PoC Chatwoot** на VPS — связать с WAHA/Evolution, ваш мозг как Agent Bot на тест-инбоксе. Решить: заменить панель или взять только коннекторы.
4. **PoC Dify** на одном тенанте — проверить, реально ли «правка промпта/базы без деплоя» ускоряет онбординг клиентов. Уточнить лицензию мультитенанта.
5. **7 CRM-паттернов** инкрементально — начать с lost_reason + activity timeline + SLA-протухание (макс. польза, мин. усилия).
6. **LangGraph** — позже, как осознанный рефактор воронки.

> Ничего из этого пока НЕ внедряется. Документ — для понимания и принятия решений.
