# DEADLINE Sales Bot — ЛОГИКА И ПРОЦЕССЫ (человеческим языком)

> Документ, чтобы ВЛАДЕЛЕЦ понял, как всё работает внутри, и мог осознанно
> подкручивать. Не айтишная карта (она в `ARCHITECTURE_RU.md`), а объяснение
> СМЫСЛА: какие есть сущности, статусы, воронка, как они связаны, как «думает»
> мозг, и пошагово — каждый бизнес-процесс. Обновлено 2026-06-17.

---

## 0. В ДВУХ СЛОВАХ

Это **AI-отдел продаж**. Клиент пишет в любой канал (сайт, WhatsApp, Telegram,
Instagram) → бот отвечает, квалифицирует, двигает по воронке, предлагает/бронирует
созвон, дожимает молчунов, а сложное — передаёт человеку. Всё видно и управляется
из панели. Бот можно держать «на поводке» (наблюдение/одобрение) или отпустить
вести самому. Каждое решение бота записывается в **Журнал решений** — видно ПОЧЕМУ.

## 1. СУЩНОСТИ (из чего всё состоит)

| Сущность | Что это | Ключевое |
|---|---|---|
| **Customer (Клиент/Лид)** | человек | имя, email, телефон, `lead_score` (0–100), `lead_temperature` (cold/warm/hot/ready/client/frozen), `profile_data` (JSON: поля, флаги, бронь созвона), `identity_keys` (по чему склеиваем каналы) |
| **Conversation (Диалог)** | переписка с клиентом в одном канале | `channel` (website/whatsapp/telegram/…), `status` (open/handed_off/resolved/abandoned/archived), `lead_stage` (стадия воронки), `lost_reason`, `wa_autonomous` (бот ведёт сам), `pending_call_suggestion`, `next_action`, `deal_value` |
| **Message (Сообщение)** | одна реплика | `role` (user/assistant/operator/system), `content`, `extra_meta` (id в канале, источник, голос и т.п.) |
| **ScheduledAction (Задача)** | что сделать и когда | `action_type` (followup_message/operator_callback/…), `executor` (bot/human), `due_at`, `status` (pending/done/cancelled), `payload` |
| **StageTransition** | запись «стадия A → B, кем» | from/to/by (bot-brain/admin/automation) — история движения по воронке |
| **BotDecision (Решение бота)** | НОВОЕ: что бот решил и ПОЧЕМУ | `decision_type`, `reason` (простым языком), `detail` — отдельный журнал прозрачности |
| **CustomFieldDef + значения** | поля под нишу | определения (Тип проекта/Бюджет/Срок…), значения в `profile_data['fields']` |
| **KBChunk (База знаний)** | кусок знаний о бизнесе | текст + эмбеддинг (вектор) для семантического поиска |
| **TrainingCorrection (Правило обучения)** | «когда X — отвечай Y» | подмешивается в ответ, ищется по смыслу |
| **AutomationRule** | no-code правило «Когда→Если→То» | триггер + условия + действия |
| **ActivityLog** | системный журнал | что/как/почему/кто на уровне СИСТЕМЫ (ошибки, конфиг, отправки) — ОТЛИЧАЕТСЯ от BotDecision |

## 2. СТАТУСЫ И СТАДИИ (две разные оси — не путать)

**Статус диалога (`Conversation.status`)** — жив диалог или убран:
- `open` — активный, в работе.
- `handed_off` — передан человеку (бот собрал контакт+бриф).
- `resolved` / `abandoned` — закрыт / заброшен.
- `archived` — убран из активных видов (слитый дубль, сидлайн при возврате лида). **Обратимо.**

**Стадия воронки (`Conversation.lead_stage`)** — где лид в продаже (это ДРУГОЕ, чем статус):
`new_lead → in_dialog → qualified → nda → on_call → tz_approved → proposal → prepayment → in_work → completed_won → post_sale` и терминальная `lost` (с причиной: price/not_our_format/competitor/delayed/no_budget/hard_stop). Стадии — кастомные под нишу (пресет переименовывает встроенные + добавляет свои).

**Температура (`Customer.lead_temperature`)** — насколько «горячий»: cold/warm/hot/ready/client/frozen. Считается по ключевым словам + остывает со временем (decay: 14д → шаг вниз, 21д → frozen). Влияет на **приоритет** в задачнике и дожиме, НЕ на текст ответа.

**Скоринг (`Customer.lead_score`)** — числовой 0–100, растёт за вовлечённость/сигналы, падает -1 за каждые 48ч тишины. Лид с `score ≥ 40` считается «вовлечённым» (его дожимаем).

**Как связаны:** клиент (Customer) ↔ его диалоги (Conversation, обычно один на канал) ↔ сообщения (Message). Диалог несёт стадию воронки + статус. Клиент несёт температуру + скор + поля. Задачи и решения привязаны к диалогу. Один человек в разных каналах склеивается в одного Customer по email/телефону/@username (см. §3.7).

## 3. БИЗНЕС-ПРОЦЕССЫ (пошагово)

### 3.1 Обработка входящей заявки (главный поток `_handle_message`, main.py)
1. Пришло сообщение (вебхук канала или сайт-виджет).
2. **Идемпотентность**: проверяем, не обрабатывали ли уже это сообщение (по нативному id) — защита от дублей при ретрае вебхука.
3. **Найти/создать клиента** (`resolve_or_create_customer_with_meta`) — по каналу+external_id, склейка по email/@username (см. §3.7).
4. **Найти/создать диалог** (`get_or_create_conversation`).
5. **Сохранить сообщение лида** (role=user).
6. **Узнавание вернувшегося** (Phase 13): если это новый диалог, но клиент уже писал раньше → бот здоровается «с памятью» (recall greeting), а не как с новым. → решение `recall_greeting`.
7. **Сборка контекста для ответа** (4 источника, см. §3.3) → **один LLM-вызов** → ответ.
8. **Сохранить ответ бота** (role=assistant).
9. **Пост-обработка ответа** (`reply_polish`) — детерминированные гарды поверх LLM (не выпытывать наценку, ≤1 вопрос, не звать в TG повторно и т.п.). Серьёзные вещи (день/время/пояс созвона) считаются КОДОМ, не доверяются LLM.
10. **Детект договорённостей**: созвон («давайте в 14:00 по Астане») → бронь/предложение (§3.5); просьба о человеке → сигнал владельцу; смена канала → задача оператору.
11. **Хэндофф**: если собран контакт (email/телефон/@username) + бриф → бриф оператору в Telegram + статус `handed_off`. → решение `handoff`.
12. **Маршрутизация ответа по каналу** (только WhatsApp, см. §3.6): наблюдение / черновик / автопилот.

⚠️ **Важно про сайт:** на website бот **ВСЕГДА отвечает сразу** (режимы наблюдение/черновик — только для WhatsApp). Если веб-лид НЕ оставил контакт → хэндофф не срабатывает, диалог остаётся `open` БЕЗ задачи → «висит». Lead-форма (`/lead-submit`) вообще не получает ответ бота (только уведомление в Telegram + запись), диалог без сообщений → крон его не трогает. **Это известный пробел — план фиксов в §5.**

### 3.2 Логика генерации ответа (мозг ответа)
Бот НЕ хранит «скрипты». Есть ДВА движка ответа (проверено по коду 2026-06-17):
- **Основной** (`build_chat_prompt`, main.py — сайт/Telegram/обычный WhatsApp) собирает из: **1) Диалог** + **2) База знаний** (KBChunk, поиск по смыслу pgvector) + **3) Правила обучения** (TrainingCorrection, поиск по смыслу) + состояние созвона/канала. ⚠️ Кастомные **поля лида сюда НЕ подмешиваются** (я в первой версии этой доки ошибочно написал «4 источника, включая поля» — это не так для основного движка).
- **Движок черновиков/автопилота** (`wa_drafts.generate_reply_text`) — для WhatsApp-черновиков и автопилота — ДОПОЛНИТЕЛЬНО учитывает **поля клиента + цель бота**. Этот движок включается флагом `WA_BRAIN=1` (по умолчанию ВЫКЛ); без него WhatsApp-автоответ идёт основным движком.
Любой движок: + системный промпт (тон, ниша) → LLM → `reply_polish` гарды → ответ. **Анти-галлюцинация:** факты из базы знаний; «серьёзные» вещи (даты/время/пояс) — детерминированный код.

### 3.3 Логика «мозга решений» (conversation_brain — отдельно от ответа)
⚠️ **Уточнение по коду (2026-06-17):** есть ДВА места, где принимаются решения, я их в первой версии смешал:
- **Живой обработчик сообщения** (`_handle_message`, main.py) — РАБОТАЕТ ВСЕГДА на каждое входящее: авто-переход стадии по воронке, бронь созвона при выборе слота, хэндофф при сборе контакта. Именно отсюда в проде идёт большинство решений (и журнал решений `call_booked/handoff/...`).
- **Отдельный «мозг решений»** `analyze_and_advance` (через `_brain_bg`) — **ГЕЙТ `WA_BRAIN=1`, по умолчанию ВЫКЛ** (пока не подтверждена стабильность под нагрузкой). Когда включён, после ручного ответа оператора он:
**Что делает analyze_and_advance (когда включён `WA_BRAIN`):** один LLM-вызов → JSON {новая стадия, договорённость о созвоне, нужен ли человек, поля}. Дальше КОД:
- **двигает стадию** вперёд (если LLM распознал прогресс) → пишет StageTransition + решение `stage_change`;
- **предлагает созвон** (не бронирует сам) если есть явная договорённость + назван день (день парсится ДЕТЕРМИНИРОВАННО из текста, не LLM — иначе путал «среду» с четвергом) → `pending_call_suggestion` + решение `call_suggested`;
- **сигналит владельцу** если лид просит человека;
- **заполняет поля** под нишу из переписки (только пустые/ранее-авто — ручные правки защищены).
Всё best-effort: сбой не роняет основной поток.

### 3.4 Логика выполнения задач (крон, каждые ~10 мин)
Фоновый крон-воркер проходит активных лидов и:
- **остывание**: температура ↓ (14д/21д), скор -1/48ч;
- **авто-перевод**: молчит на стадии «диалог» дольше порога (деф. 7д) → `lost(delayed)` → решение `silence_lost`;
- **прогрев/дожим**: вовлечённый молчун (score≥40) → бот мягко пингует по **каденции** (напр. «1ч, 1д, 3д» — настраивается); счётчик сам обнуляется, когда лид ответил; стоп при ответе/брони/остывании. → решение `nudge_sent`;
- **win-back**: проигранный по восстановимой причине (цена/отложил/нет бюджета — НЕ жёсткий отказ) старше N дней → задача оператору (по умолчанию выключено). → решение `winback_task`;
- **отправка bot-followup**: созревшие задачи `executor=bot` крон шлёт сам (Telegram).
Плюс «обслуживание» (дедуп сообщений, слияние разорванных карточек, чистка).
**Антибан:** все исходящие через троттл (≥5с между + случайная задержка) + дневной потолок.

### 3.5 Логика созвона (надёжность дат/времени)
- День недели и относительные дни («завтра», «послезавтра») — **детерминированный парсинг текста** (не LLM).
- Часовой пояс лида — по префиксу телефона ИЛИ по явной фразе «по Астане/Москве» (переопределяет). Время в календарь — в правильном АБСОЛЮТНОМ UTC; в карточке показываются ОБА времени («14:00 Астана = 16:00 Пхукет»).
- Бот **предлагает** созвон (не бронирует молча) → менеджер подтверждает/правит в карточке → создаётся бронь + напоминания (-24ч/-3ч/-1ч). Решения: `call_suggested` → `call_booked`/`call_rescheduled`/`call_cancelled`.

### 3.6 Логика передачи боту (3 режима — только WhatsApp)
- **👀 Наблюдение** — бот видит и готовит ответ, но клиенту НЕ пишет; оператор одобряет каждый ответ в карточке.
- **📝 Черновик** — бот шлёт черновик+ТЗ в Telegram на ✅/🚫.
- **🤖 Автопилот** (`wa_autonomous`) — бот сам отвечает и ведёт диалог; в любой момент «Взять на себя».
На сайте бот всегда отвечает сам (этих гейтов нет). Передача конкретного лида боту — флаг `wa_autonomous` на диалоге (зелёная рамка в Переписках и Задачнике).

### 3.7 Логика идентификации (склейка лида между каналами)
Один человек пишет с сайта и из WhatsApp — это должен быть ОДИН Customer. Якорь склейки:
1. **email** (главный) — лид дал email → склеиваем диалоги.
2. **@username Telegram** (если нет email).
3. **телефон** — пока НЕ используется для склейки (фаза 1: email) — это пробел (план §5).
WhatsApp-реклама под скрытым `@lid` → пытаемся разрезолвить реальный телефон (WAHA), иначе ручной ввод; как только телефон есть — `@lid` и `@c.us` карточки схлопываются.

### 3.8 Логика обучения бота (как «научается»)
- Оператор в карточке жмёт **«🎓 научить бота»** на своём удачном ответе → создаётся `TrainingCorrection` («в такой ситуации отвечай похоже»).
- Или быстрое правило одной строкой в «Мозге».
- Эти правила ищутся по смыслу (pgvector) и подмешиваются в ответ (§3.2, источник 3). Проверяются на конфликт.
- База знаний (KBChunk) пополняется загрузкой документов; при загрузке дедуп одинаковых кусков.

### 3.9 Логика записи логов (ДВА разных журнала — не путать)
- **Системный журнал (ActivityLog)** — что/как/почему/кто на уровне СИСТЕМЫ: ошибки, смена конфигурации, подключение каналов, массовые отправки. Настройки → расширенные → «Логи системы». Хранится 30 дней.
- **Журнал решений бота (BotDecision)** — НОВОЕ, ОТДЕЛЬНО: каждое автономное решение бота с причиной простым языком (стадия/созвон/дожим/win-back/хэндофф/recall/silence→lost). В карточке лента «🤖 Решения бота» + Настройки → расширенные → «Журнал решений бота». Хранится 60 дней. Цель — прозрачность: видно, ПОЧЕМУ бот так сделал, и можно подкрутить правило.
Оба пишутся **best-effort** — сбой записи не ломает основной поток; не держат коннект во время LLM (урок инцидента-виса 06-02).

### 3.10 Логика revenue (сколько денег принёс бот)
В карточке (расширенный режим) проставляется **сумма сделки** (`deal_value`). В Аналитике — выручка по воронке/каналам, средний чек, в работе/потеряно. Это аргумент «бот окупается».

## 4. КАК ВСЁ СВЯЗАНО (одна картина)

```
Клиент пишет в КАНАЛ ──► Идемпотентность ──► Customer + Conversation + Message(user)
        │
        ▼
   МОЗГ ОТВЕТА (4 источника + 1 LLM) ──► Message(assistant) ──► reply_polish ──► ответ в канал
        │                                                                  (WhatsApp: наблюдение/черновик/автопилот)
        ▼
   МОЗГ РЕШЕНИЙ (analyze_and_advance) ──► стадия↑ / созвон / поля / сигнал ──► StageTransition + BotDecision
        │
        ▼
   ВОРОНКА (lead_stage) + ТЕМПЕРАТУРА + СКОР ──► приоритет в ЗАДАЧНИКЕ
        │
        ▼
   КРОН (10 мин): остывание · авто-lost · дожим-каденция · win-back · bot-followup ──► ScheduledAction + BotDecision
        │
        ▼
   ЗАДАЧНИК (что дальше: бот сам / на одобрение / за человеком) ◄── оператор работает
        │
        ▼
   ХЭНДОФФ (контакт+бриф) ──► Telegram оператору ──► status=handed_off ──► человек закрывает сделку (deal_value)
```

CRM HubSpot — опциональное зеркало (очередь, не блокирует бота). База знаний и правила обучения питают «мозг ответа». Журнал решений делает всё прозрачным.

## 5. ИЗВЕСТНЫЕ ПРОБЕЛЫ ЛОГИКИ (что сейчас «хромает» — план фиксов)

Выявлено ресёрчем + разбором кода 2026-06-17:
1. **Веб-лид без контакта «висит»** — бот ответил, лид не дал контакт → нет задачи, нет статуса. *Фикс:* статус «без контакта» + авто-задача оператору + последнее CTA «оставьте email/номер» перед таймаутом; отдельная колонка «Без контакта», чтобы не засоряли список.
2. **Lead-форма без следующего шага** — диалог без сообщений, крон пропускает. *Фикс:* авто-задача при `/lead-submit` (или fallback next_action из данных формы без LLM).
3. **Нет удаления/архивации лида из UI** — есть только `clear_demo` для демо. *Фикс:* «Архивировать» (мягко, обратимо, undo) + раздел «Архив» + жёсткое удаление только оттуда с подтверждением. НЕ удалять физически (UTM/аналитика).
4. **Тестовые лиды неотличимы** — свои тесты висят среди реальных. *Фикс:* IP-фильтр своих тестов + скоринг junk/suspicious/real при захвате (фиктивный email/имя, одноразовый домен, бот-тайминг) → авто-архив мусора, флаг подозрительных.
5. **Склейка только по email/@username** — телефонные лиды (WhatsApp) дублируются. *Фикс:* добавить merge по нормализованному телефону.
6. **Задачник — единица размыта** — карточка это задача или лид? *Фикс (редизайн):* единица = ЛИД, требующий шага; 3 зоны «Одобри сейчас / Твой ход / Бот ведёт»; статус-индикатор бота на карточке; алерт «затык» (лид без движения и без задачи). Подробности — в предложении по редизайну.

## 6. ГДЕ ЧТО КРУТИТЬ (для владельца)
- **Тон/знания бота** → «Мозг» (системный промпт, база знаний, правила обучения).
- **Цель бота / режим WhatsApp / каденция дожима / win-back** → Настройки → Поведение.
- **Стадии воронки / поля под нишу / автоматизации** → Воронка / Поля / Автоматизации.
- **Скрыть функции под нишу / расширенные настройки** → Настройки.
- **Понять, почему бот так сделал** → «🤖 Решения бота» (в карточке и в расширенных настройках).
