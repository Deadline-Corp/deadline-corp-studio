# DEADLINE — WhatsApp в системе: как устроено, состояние, эксплуатация

_Актуально на 2026-06-15. Единая точка правды по WhatsApp-части бота: что
подключено, откуда данные, как лиды попадают в стадии, как работает умное
авто-ведение, какие предохранители, ограничения и как всем пользоваться._

---

## 1. Цель и охват

Бот DEADLINE — единая обработка лидов из всех каналов (сайт-виджет, Telegram,
Instagram/Messenger, **WhatsApp**) в одной панели «Переписки» + воронка. По
WhatsApp: видеть **все** переписки номера, понимать **кто на какой стадии**,
**сам вести лида** (собрать задачу → дать примерную цену → созвон), не писать
клиентам без ведома оператора.

Состояние: **~64 диалога** в системе (WhatsApp + сайт). Мозг — **Gemini 2.5 Flash**.

---

## 2. Архитектура подключения

Официальный WhatsApp Cloud API не подошёл (нужна верификация бизнеса). Поэтому —
**self-hosted WAHA** (`devlikeapro/waha`, неофиц. обёртка над Baileys) на Contabo
VPS (`84.247.148.135:3000`, Docker, движок NOWEB). Номер привязан «связанным
устройством» по QR — без верификации, без лимитов на чаты, $0 за софт.

```
WhatsApp (телефон)
   │  связанное устройство (QR)
   ▼
WAHA (VPS, NOWEB + store)
   │  webhook message.any  ──► /webhooks/waha  (ВХОДЯЩИЕ + fromMe-эхо, онлайн)
   │  REST /chats[/messages] ─► sync_waha_history (ИСТОРИЯ, по кнопке)
   ▼
DEADLINE бот (Railway): Customer + Conversation(channel=whatsapp) + Message
   │
   ├─► Панель «Переписки» + воронка + классификация + стадия
   └─► Умное авто-ведение (брейн): стадия + бронь созвона + сигнал владельцу
```

### Приём вебхуков — ACK-first + bounded (КРИТИЧНО для стабильности)
`/webhooks/waha` и `/webhooks/greenapi` отвечают **200 МГНОВЕННО**, а вся тяжёлая
работа (парс вкл. голос, `_handle_message`, отправка, авто-ведение) идёт в **фоне**
через `_process_wa_payload` с **семафором (1 разом)** и собственной DB-сессией.

Зачем: архитектура = async FastAPI + **sync SQLAlchemy** → каждый checkout DB
БЛОКИРУЕТ event loop; если обрабатывать инлайн и хэндлер висит (LLM держит
коннект), WAHA не получает 200 → ретраит → бэклог → пул исчерпан → **процесс
заморожен** (инциденты 06-02 и 06-15). ACK-first рвёт петлю ретраев, семафор
ограничивает нагрузку. **Правило на будущее: НЕ делать LLM, держа request/session
DB-коннект; новые LLM-пути — в фоне, bounded, со своей сессией.**

### Ключевые файлы
- `channels/waha.py` — парсер вебхука + чтение истории; `chat_id_from_waha_id`,
  `wa_chat_id`/`wa_peer_type` (@lid vs телефон).
- `services/whatsapp_sync.py` — `sync_waha_history()`: идемпотентный импорт
  (дедуп по `waha_id`) + классификация + **сверка (reconcile)**.
- `services/lead_classifier.py` — лид/не-лид + категория + температура + стадия.
- `services/wa_drafts.py` — генерация предложенного ответа (промпт + цены +
  `_clean_draft`), штамп свежести `based_on_count`, `is_stale`.
- `services/conversation_brain.py` — **умное авто-ведение** `analyze_and_advance`
  + `sweep_recent` (см. §5).
- `main.py` — вебхуки (ACK-first), `_process_wa_payload`, `_wa_send` (резолв @lid),
  `_brain_bg`, `_record_wa_operator_message`.
- `admin_api.py` — `/whatsapp/sync|status|import-leads|dedup|prepare-drafts|`
  `clean-phantoms|brain-sweep`, `/conversations/*` (карточка, кнопки, созвон).

## 3. Источники диалогов

1. **Мета-реклама (click-to-WhatsApp)** — основная масса. Жмут рекламу → пишут на
   номер. В метаданных `externalAdReply`. Реальные лиды, не мусор. Приходят под
   скрытым `@lid` (телефон недоступен).
2. **Импорт 8 разобранных лидов** из прошлой сессии (`/whatsapp/import-leads`).
3. **Живые входящие + ручные ответы** после подключения (вебхук, в т.ч. fromMe-эхо).

## 4. Воронка, стадии, имена, цены

### Стадии (`lead_stage`)
`new_lead` 🆕 → `in_dialog` 💬 → `qualified` ✅ → `on_call` 📞 → `proposal` 📄 →
`prepayment` 💰 → `completed_won` 🏁 · `lost` ❌. (`funnel_store.py::BUILTIN_STAGES`.)

`qualified` ставится **только когда лид описал конкретную задачу проекта** (не на
«привет/расскажите подробнее» — это `in_dialog`).

### Кто двигает стадию
- Импортным 8 — вручную из разбора.
- Синхронизированным — классификатор (Gemini) по переписке, только из `new_lead`.
- Живой трафик / ручные реплики — **брейн** (см. §5) двигает ВПЕРЁД (никогда назад);
  оператор может сменить вручную («Сменить стадию»).

### Имена (никогда «Без имени»)
`_wa_display_name`: имя → телефон → `+номер` (реальный @c.us) → `WhatsApp •хвост4`
(скрытый @lid, телефон недоступен). Фронт показывает `customer.display_name`.

### Цены (стартовые планки «от $X», точная сумма — на созвоне)
Лендинг от **$300** · Интернет-магазин от **$700** · Telegram-бот от **$300** ·
Telegram Mini App от **$500** · AI-бот от **$300**. Зашиты в `prompts.py` (#ЦЕНЫ)
и `services/wa_drafts.py`. Бот называет планку, когда понятен ТИП проекта;
финальную сумму не называет.

### Температура (`lead_temperature`): `cold/warm/hot/ready/client/frozen`
По сигналам в сообщениях + decay при молчании (`services/temperature.py`).

## 5. Умное авто-ведение (брейн) — флаг `WA_BRAIN`

`services/conversation_brain.py::analyze_and_advance` по каждой новой реплике —
лида ИЛИ ручного ответа оператора с телефона — одним LLM-вызовом (Gemini, JSON)
решает и применяет:
1. **Стадия вперёд** (forward-only) по смыслу переписки.
2. **Бронь созвона** — если согласовано **конкретное время** («завтра в 14:00»):
   ставит `booked_call_at` + стадия `on_call` + напоминания (лиду в его поясе,
   владельцу по Пхукету) — те же примитивы, что ручная бронь из карточки. Вязкие
   договорённости без часа («в первой половине дня») НЕ бронятся.
3. **Сигнал владельцу** в Telegram, если лид явно просит человека/созвон.
4. **Освежение черновика** — генерит предложенный ответ в фоне (не в GET-пути!),
   если его нет/устарел → панель всегда показывает актуальный ответ.

Часовые пояса: `scheduling.lead_tz_from_phone` (77→Астана UTC+5, 79/78→Москва,
971→Дубай, 995/374→Тбилиси/Ереван, иначе Пхукет UTC+7). 12:00 Астаны = 14:00 Пхукета.

### Где запускается
- В фоне после каждого входящего/ручного сообщения (`_brain_bg`, своя сессия,
  семафор ≤2).
- Периодический `sweep_recent` в кроне (каждые ~10 мин): берёт недавно активные
  диалоги с НОВЫМИ сообщениями (дешёвый count-чек по `brain_last_count`), каждый
  обрабатывает В СВОЕЙ короткой сессии (коннект возвращается в пул между LLM).
- Вручную: `POST /admin/api/whatsapp/brain-sweep` (для теста/догона).

### Предохранители (env)
- **`WA_BRAIN=1`** — включает всё авто-ведение + фоновое освежение черновиков +
  cron-sweep. **`WA_BRAIN` пусто/0 → всё ВЫКЛ** (бот только отвечает на входящие
  как раньше, черновик — по кнопке «🤖 Предложить ответ»).
- **`WA_WEBHOOK_PAUSE=1`** — аварийный стоп обработки входящих (разгрузить прод).
- Менять в Railway vars → авто-редеплой. Откат при проблемах: снять `WA_BRAIN`.

`conversation_detail` (карточка) **НЕ делает LLM** — только отдаёт готовый черновик
(панель его поллит, LLM в GET вешал бы пул). Черновик всегда свежий за счёт брейна.

**Выровненный движок ответа.** Когда `WA_BRAIN=1`, ответы бота в WhatsApp (и
автопилот, и удерживаемый черновик) генерятся ТЕМ ЖЕ движком, что предлагаемые
черновики (`wa_drafts`: собрать задачу → «от $X» → созвон) — а не слабым
first-turn `build_chat_prompt`. Так «бот пишет сам» = качество одобряемых
черновиков. `max_tokens=2048` (gemini-2.5 тратит часть на thinking — при 1200
ответ обрывался).

**Голосовые.** Входящие голосовые: WAHA отдаёт media с mime `audio/*` (тип пустой
в NOWEB → распознаём по mime) по URL `localhost:3000` (переписываем на публичный
`waha_base_url`) → скачиваем → Groq Whisper → текст в переписку → брейн понимает
вместе с остальным. Работает на НОВЫХ голосовых; история-синк голос пока не
транскрибирует.

## 6. Кнопки карточки (все рабочие)

| Кнопка | Что делает |
|---|---|
| 👤 Взять на себя / 🤖 Вернуть боту | Оператор перехватывает диалог (бот молчит) |
| Сменить стадию… | Ручной перевод по воронке (пишет историю) |
| ⚡ Пинок | Черновик-дожим от LLM / отправить сразу |
| 📋 Задача | Задача себе/боту |
| 🧭 Что делать | LLM-подсказка следующего шага |
| 📞 Назначить/Перенести/Отменить созвон | Ручная бронь из карточки (datetime) |
| 🔁 Регулярный | Повторяющийся клиент (расписание) |
| 📋 Назначить на… | Назначить лида на сотрудника |
| ✅ Отправить / 🔄 Переформулировать / 🚫 Отклонить | Одобрить/перегенерить/отклонить черновик |
| 🤖 Бот ведёт сам | Автономный режим для этого диалога |
| ✍️ Ответить вручную | Развернуть поле ручного ответа (по умолчанию свёрнуто) |

**UI карточки:** блок «🤖 Бот предлагает ответить» **сворачивается** (▾/▸), окно
ручного ответа по умолчанию **свёрнуто** — чтобы видеть саму переписку, а не два
больших поля ввода.

Режим по умолчанию — **наблюдение**: бот видит и предлагает, но клиенту сам не
пишет, пока оператор не одобрит (✅) или не разрешит автономку.

## 7. Сверка и чистота данных

- **reconcile** (`sync_waha_history(reconcile=True)`, кнопка «🔄 Подтянуть все
  переписки»): WAHA = источник правды. Импорт новых + удаление **фантомных**
  локальных сообщений (assistant без `waha_id`/`approved_via`/`delivered`) +
  сверка числа сообщений БД↔WAHA.
- **`/whatsapp/clean-phantoms`** — глобально вычистить фантомы (сообщения бота,
  которых нет в WhatsApp). Фантомы появляются, если бот сгенерил ответ, но он не
  ушёл (не-observe режим + сбой отправки). В режиме наблюдения фантомов нет.
- **Отправка @lid:** рекламные лиды под `@lid`; `_resolve_wa_chat_id` берёт
  настоящий JID из истории — иначе WAHA отвечает 201, но клиент НЕ получает.

## 8. Ограничения (честно)

1. **`@lid` не резолвится в телефон** (WAHA `pn:null`) → рекламные чаты не склеить
   автоматически с импортированными по номеру; дедуп по имени/вручную.
2. **Нативные авто-приветствия WhatsApp Business невидимы** (шлёт сервер Meta мимо
   устройства) — только офиц. API.
3. **История только активных чатов**; полный backfill — через ре-скан QR.
4. **Неофициальное подключение** (WAHA) — риск бана номера; держать запасной.
5. **Единый процесс + sync SQLAlchemy** — тяжёлые LLM под нагрузкой требуют
   ACK-first/bounded/фон (см. §2). Не гонять параллельно sync + bulk-LLM по проду.

## 9. Эксплуатация (шпаргалка)

- **Подтянуть/сверить:** Каналы → WhatsApp → «🔄 Подтянуть все переписки».
- **Полный backfill:** ре-скан QR (logout сессии WAHA → скан в WhatsApp →
  Связанные устройства) → кнопка синка.
- **Режим бота:** Каналы → WhatsApp → 👀 наблюдение / 📝 черновик / 🤖 авто.
- **Включить умное авто-ведение:** Railway var `WA_BRAIN=1` (после проверки
  стабильности). Аварийный стоп: `WA_WEBHOOK_PAUSE=1` или снять `WA_BRAIN`.
- **Мозг:** Gemini 2.5 Flash (`LLM_PROVIDER=gemini`). Дешевле — `gemini-2.5-flash-lite`.
- **Деплой:** `railway up --service 9cdf9db1-...` (env production); GitHub-пуш сам
  НЕ деплоит ветку `feature/call-booking`. Токен — `D:\deadline-bot-local\env\env`
  (`RAILWAY_API_TOKEN`). Админ-API — Bearer `TRAINING_AUTH_TOKEN` (из Railway vars).
  Миграции на старте (`alembic upgrade head`). Откат-флаги мгновенны (env→redeploy).
- **Проверка выката:** `railway status` → deployment ID меняется, когда новый
  healthy; `GET /health` (200 + `db_connected`).

## 10. Бэклог

- `@lid → телефон` маппинг + дедуп импортных лидов с рекламными двойниками.
- Долгосрочно: убрать sync-SQLAlchemy-под-LLM (async-движок или threadpool для DB)
  — снимет класс «вис под нагрузкой» целиком.
- Двусторонняя Google-синхра календаря (нужен Google OAuth владельца).
- Решение по нативным авто-приветствиям (офиц. WhatsApp Business API — если нужно).
