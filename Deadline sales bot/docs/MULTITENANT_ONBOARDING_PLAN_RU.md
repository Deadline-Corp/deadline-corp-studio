# Self-service онбординг под нишу (план + дебаты) — 2026-06-13

> Цель: новый владелец (напр. Кирил, клининговая компания) сам проходит онбординг →
> анкета → система настраивается под него (воронка, мозг, инфо о компании, прайс) —
> БЕЗ участия Claude/разработчика. Планируем, потом реализуем.

---

## 1. ЧТО УЖЕ ЕСТЬ (фундамент)

- **Копия на клиента:** `deploy/new-client.sh <slug> "<Бизнес>"` → отдельный Railway-проект
  (свой Postgres, токены, домен) + деплой кода. Обновления — `deploy/update-all.sh`.
- **Tenant-слой:** `tenants/<slug>/config.yaml` + `system_prompt.md` (пока только deadline-corp).
- **Онбординг-визард** (Onboarding.tsx) + workspace (имя бизнеса, niche_key, флаг).
- **Пресеты ниш** (`/presets`, `/presets/apply`) — нишевый набор: стадии воронки + поля
  лида + правила автоматизаций в 1 клик (паттерн GHL Snapshots).
- **Мозг:** редактируемый prompt/правила (вкладка «Мозг», training), мультипровайдер
  (OpenRouter/Gemini/Groq — «подключи свои мозги»).
- **KB:** markdown в `kb/` → индексируется (pgvector). Self-service наполнения пока нет.
- **Команда, цель бота, белый лейбл, ICS-календарь** — настраиваются из панели.

### Главный зазор
`new-client.sh` ставит новой копии `TENANT_SLUG=deadline-corp` → она наследует НАШ
промпт/прайс/KB. Нет шага «сгенерировать конфиг ПОД КЛИЕНТА из анкеты». Заполнить
вручную файлы tenants/<slug>/ — это «через разработчика», а нужно self-service.

## 2. ДЕБАТЫ (спорные вопросы + мои решения)

### Д1. Как генерится конфиг под нишу: пресеты / LLM-генератор / гибрид?
- Пресеты — быстро, но только предопределённые ниши (клининга может не быть).
- Чистый LLM-генератор — гибко под любую нишу, но риск «галлюцинаций» в проде.
- **РЕШЕНИЕ — ГИБРИД с ревью.** Онбординг-анкета (+опц. ссылка на сайт компании) →
  **LLM-генератор конфига** выдаёт ЧЕРНОВИК: `system_prompt` (тон+оффер), `kb` (услуги/
  цены/FAQ), рекомендованный пресет воронки, прайс, цель бота. Владелец **видит и правит**
  черновик в панели → «Применить». Пресеты остаются как стартовые шаблоны. Так — и гибко
  (любая ниша), и безопасно (человек подтверждает перед боевым режимом).

### Д2. Нужен ли «агент» внутри и какой именно?
Да, но **узкий и структурный**, не автономный «делающий всё».
- **«Конфиг-агент»:** инструменты = (1) `fetch_url` (скачать сайт компании клиента),
  (2) `llm_extract` (вытащить услуги/цены/тон/FAQ), (3) `write_tenant_config` (записать
  system_prompt + KB + применить пресет через наш же API). Возвращает черновик на ревью.
- Это детерминированный пайплайн «анкета+сайт → JSON-конфиг → наши API», а не свободный
  агент. Безопасно, воспроизводимо, дёшево.

### Д3. Hermes + Gemini + управление компьютером — да или нет?
**Против — для онбординг-конфига.** Управление компьютером/браузером (Hermes) нужно там,
где НЕТ API. У нас API ЕСТЬ (admin API, пресеты, индексация KB) → конфиг строим прямыми
вызовами (LLM→API), а не кликами по экрану. Computer-control здесь — хрупко, медленно,
лишняя точка отказа. **Где Hermes/браузер оправдан** (отдельно, opt-in): задачи без API —
например «залогиниться в Meta и прокликать подключение WhatsApp за клиента». Но и это
рискованно (баны, 2FA) — лучше клиент сам по нашей инструкции. Итог: **онбординг — в
приложении (LLM+API); браузер-агент — узкий opt-in только для ресёрча/действий без API.**

### Д4. Деплой: копия на клиента или один мультитенант-апп?
- Сейчас — копия на клиента (изоляция, просто, ~$5-10/мес). Минус: апдейты через
  update-all.sh, и баг с TENANT_SLUG.
- **РЕШЕНИЕ:** для пилота (Кирил + пара товарищей) — **оставляем копию на клиента**
  (надёжнее, изолированнее). Чиним new-client.sh: генерит СВОЙ tenant slug + запускает
  конфиг-агент. Полноценный мультитенант (один апп, много арендаторов в БД) — когда
  пойдут платящие клиенты десятками (отдельный крупный этап).

### Д5. Что собирает анкета онбординга (вход для конфига)?
Бизнес и ниша; что продаёте (услуги + вилки цен); цель бота (созвон/заявка/продажа);
тон; частые возражения; рабочие часы/слоты созвонов; каналы; команда; (опц.) ссылка на
сайт/прайс. → маппится в: system_prompt, KB, пресет воронки, прайс, bot_goal, окно
слотов, команда.

### Д6. «Боевая для DEADLINE» vs «версия для товарища»
Одна кодовая база — два Railway-проекта. DEADLINE — текущий прод (уже живой). Кирил —
новая изолированная копия (`new-client.sh cleaning "Клининг Кирила"`), он проходит
онбординг сам. Никакого форка кода.

## 3. ПЛАН РЕАЛИЗАЦИИ (по фазам, после согласования)

- **Фаза 0 — починить new-client.sh:** генерить уникальный `TENANT_SLUG=<slug>` +
  скаффолдить `tenants/<slug>/` (пустой config.yaml + system_prompt.md из шаблона).
- **Фаза 1 — анкета онбординга:** расширить визард полями из Д5 (+ поле «ссылка на сайт»).
- **Фаза 2 — конфиг-агент (ядро):** endpoint `/admin/api/onboarding/generate` — берёт
  ответы анкеты (+опц. fetch сайта) → LLM генерит черновик {system_prompt, kb_md,
  preset_key|stages, prices, bot_goal}. UI «Предпросмотр и правка» → «Применить»
  (пишет tenant-файлы, индексирует KB, применяет пресет/стадии).
- **Фаза 3 — нишевые пресеты:** добавить пресет «Клининг» (и ещё 2-3 частых) как
  стартовый шаблон; генератор может стартовать от ближайшего пресета.
- **Фаза 4 — пилот Кирил:** деплой его копии → он проходит онбординг end-to-end →
  прогоняем полный путь (лид→квалификация→созвон→карточка) на его конфиге.
- **Фаза 5 (позже):** браузер-агент (opt-in, песочница) для ресёрча; полноценный
  мультитенант при масштабировании.

Каждая фаза — отдельные коммиты + тест на копии (НЕ на боевом DEADLINE).

## 4. ОТКРЫТЫЕ ВОПРОСЫ К ПОЛЬЗОВАТЕЛЮ

1. **Степень авто-генерации:** ок ли «LLM генерит черновик → владелец правит → применяет»
   (рекомендую), или хочешь полностью автоматически без ревью?
2. **Сайт компании:** даёшь конфиг-агенту скачивать сайт клиента для авто-наполнения
   KB/прайса (быстрее, но надо ревью), или только из анкеты руками?
3. **Деплой Кирилу:** ок «копия на клиента» (отдельный Railway ~$5-10/мес), или хочешь
   сразу мультитенант в одном аппе (дольше делать, но дешевле на масштабе)?
4. **Кто платит за инфраструктуру** копии на время пилота (Railway/LLM-ключи) — ты даёшь
   свои ключи, или клиент заводит свои (автономность, но сложнее для не-технаря)?
5. **Боевая DEADLINE:** оставляем как есть (текущий прод), а эксперименты — только на
   копии Кирила? (рекомендую — не рисковать живым трафиком).

## 5. УГЛУБЛЁННЫЕ ДЕБАТЫ v2 (2026-06-13) — после уточнений + данных по стоимости

### Данные по Railway (ресёрч 2026)
- Railway биллит по **суммарному потреблению аккаунта**, НЕ по числу проектов (проектов
  — неограниченно). Но 5 отдельных копий = 5 Postgres = ~5× RAM (Postgres держит min
  ~256 MB всегда). Scale-to-zero на Hobby НЕТ → idle тикает деньгами.
- **Копия-на-клиента ≈ $23/мес (5 клиентов). Мультитенант (1 app+1 БД) ≈ $14/мес.
  Мультитенант + бесплатный Neon-Postgres ≈ $5-7/мес за всех.** Бесплатного Railway
  (кроме $5 trial 30 дней) нет.

### Д7. Копия-на-клиента vs мультитенант — ПЕРЕСМОТР
Прошлая рекомендация (копия) была про «быстро и изолированно». Но твои новые
требования — **дёшево + управление из одного места + конфиги похожие** — это профиль
МУЛЬТИТЕНАНТА.
- **РЕШЕНИЕ:** целимся в **один мультитенант-апп для всех пилотов** (отдельный от
  боевого DEADLINE) + **Neon free Postgres**. Все товарищи (Кирил, психолог, …) =
  записи-арендаторы в одном аппе, маршрутизация по нише/боту/домену. Новый клиент =
  новая конфигурация, БЕЗ нового деплоя. Управление — из одной супер-админки. ~$5-7/мес.
- **Цена входа:** это рефактор single-tenant→multitenant (роутинг входящих по арендатору,
  per-tenant конфиг в рантайме, изоляция данных tenant_id, per-tenant секреты). DEADLINE
  при этом не трогаем (отдельный проект).
- **Альтернатива для скорости:** Стадия 1 — копия для ПЕРВОГО пилота (Кирил), чтобы
  быстро отладить онбординг/конфиг-агент; Стадия 2 — построить мультитенант-апп и
  перенести пилоты. Тебе выбрать: «дёшево+правильно сразу» (мультитенант, дольше до
  первого теста) или «быстро сначала» (копия для Кирила → потом мультитенант).

### Д8. «Вывалить всё» → агент раскладывает (интейк знаний)
Экран онбординга «Знания о компании»: вставить/загрузить текст сайта + регламенты +
прайсы, опц. ссылка (агент скачивает), опц. голос (транскрипт через Groq Whisper —
он уже есть в боте). **Конфиг-агент (LLM)** переваривает дамп и РАСКЛАДЫВАЕТ:
- → **МОЗГ** (system_prompt): тон, позиционирование, оффер, что можно/нельзя;
- → **KB** (индекс): услуги, цены, FAQ, политики;
- → **ВОРОНКА**: ближайший пресет ниши + правки;
- → **НАСТРОЙКИ**: часы, цель, каналы.
Возвращает структурированный черновик на ревью. Человек не заморачивается — агент
сам решает, что куда. Сайт = ЧАСТЬ источника (часто устаревший), остальное — из дампа/
голоса/анкеты.

### Д9. Продукты часто меняются → лёгкая перенастройка
Отделяем **волатильное (продукты/цены) от стабильного (мозг)**. Отдельный
редактируемый **«Каталог услуг»** на арендатора (список: название / цена «от» /
описание) → авто-переиндексация в KB при сохранении → бот всегда актуален. Обновление
текстом или голосом в любой момент, без правки промпта. Так «продукты меняются» —
это правка списка за 10 секунд, а не переписывание мозга.

### Д10. Управление из одного места
**Супер-админка (tenant console):** один экран — список всех арендаторов, добавить
нового, открыть конфиг каждого, статус/метрики. Естественно ложится на мультитенант
(один апп). На копиях-на-клиента это были бы N разных панелей — ещё довод за мультитенант.

### Д11. Ключи: наши сейчас, легко сменить
Слой per-tenant секретов: дефолт — НАШИ ключи (LLM/каналы), у каждого арендатора —
переопределение в его Настройках, и это **отражено в обучении** («хотите свой ключ —
вот сюда»). Сейчас все на наших; переключение на свои — в 1 поле, когда захотят.

### Д12. Обучение/тур — как сейчас и как надо
**Как сейчас:** spotlight-тур уже есть (Tour.tsx, 12 шагов, `startTour`): затемняет
экран, подсвечивает элемент, карточка объясняет; можно пропустить/повторить из Настроек.
**Как надо (доработка):** авто-старт ПОСЛЕ онбординга + **под цель ниши** (для клининга —
акцент на «заявка→замер/созвон→расчёт», для психолога — «запись на сессию»). Тур
объясняет, ГДЕ что настраивать под его задачу. Сделаем тур-контент зависимым от niche_key.

### Д13. Путь «сам пройду под Кирила → отдам ему»
1. Завожу арендатора «Клининг Кирила», прохожу онбординг ПОЛНОСТЬЮ как он (дамп его
   инфо → агент разложил → правлю), подключаю каналы (на наших ключах), гоняю полный
   путь лид→квалификация→созвон→карточка. 2. Фиксы. 3. **Сброс тест-данных этого
   арендатора** (per-tenant clean, не глобально). 4. Отдаю Кирилу ссылку+токен — он
   заходит, тур проводит, он донастраивает. Потом — психолог и т.д. как новые конфиги.
