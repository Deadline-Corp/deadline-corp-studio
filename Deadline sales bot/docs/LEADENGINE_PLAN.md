# LeadEngine — целевой движок состояния лида (план и дорожная карта)

> Источник: 2 многоагентных дебата (редизайн задачника + оркестрация системы) 2026-06-17,
> агенты читали реальный код. Этот документ — рабочая дорожная карта; идём по шагам за
> флагами, проверяя каждый на проде. НЕ большой взрыв (урок инцидента пула 06-02).

## 0. Цель и решения владельца (зафиксировано)
- **Цель:** бот ведёт продажи сам, человек надзирает/правит/обучает; со временем отдаём
  боту всё больше, в идеале человек только смотрит. Сейчас бот туповат → полу-авто.
- **Календарь:** внутренний (в панели). Внешний Google — опционально позже (односторонний
  push). Двусторонняя синхронизация пока НЕ делаем.
- **Автономия:** старт — ВСЁ на одобрение (чистый копилот). Поднимать пороги per-срез
  ТОЛЬКО по накопленной статистике одобрений с явным подтверждением. Не жёсткий потолок
  по стадии.
- **Число операторов** — не важно (модель — копилот под надзором, не мульти-оператор).

## 1. Целевая архитектура (как «всё сходится»)
- **StageMachine** (поверх существующего `funnel.py`) — ЕДИНСТВЕННЫЙ писатель
  `conversation.lead_stage`; всегда пишет `StageTransition`; единый хук `on_stage_changed`
  (CRM-зеркало, постановка/снятие задач, снятие брони при lost). Удалить второй движок
  `conversation_brain._FORWARD`.
- **apply_plan** — ЕДИНСТВЕННАЯ материализация намерения в факты: статус + задача + бронь +
  ответ + сигнал в ОДНОЙ транзакции под row-lock по `customer_id` + дебаунс батча сообщений.
  Рассинхрон становится структурно невозможен.
- **Надзорный мозг** = РАСШИРЕННЫЙ `services/diagnostics.py` (он уже есть: `run_diagnostics`
  + `auto_heal`). Два слоя: (1) синхронный guard в `apply_plan` на критичные инварианты
  (I2 double-booking, I4 takeover⊻бот); (2) асинхронный reconciler в кроне на дрейф (I1–I8).
  Исходы: AUTO-FIX (обратимо, с `BotDecision actor=supervisor`) или SIGNAL-ONLY (в «Затык»).
  НЕ событийная шина (риск пула; reconciler идемпотентен и переживает рестарт).
- **LeadPlan-копилот** — один объект `LeadPlan` на диалог заменяет 3 рассогласованных выхода
  (`next_action`-лейбл + `pending_call_suggestion` + `pending_wa_draft`): {намерение,
  confidence, предлагаемая стадия, задачи, событие, черновик+provenance, риск-флаги, mode}.
  Человек видит план карточкой → Применить/Править/Боту. Правка → исполняется + пишется в
  `plan_feedback` → обучение (правки текста → `TrainingCorrection`, статистика → калибровка
  автономии).
- **Намерение→действие при туповатой LLM:** LLM только РАСПОЗНаёт {kind, confidence, slots};
  МАТЕРИАЛИЗУЮТ детерминированные стражи (`services/guards.py`: парс дня, «есть ли слово
  звонок», «отложил время», «молчание≠согласие») + `funnel.validate_transition` + apply_plan.
  Надёжность не от точности модели, а от детерминированного исполнителя с инвариантами.

## 2. Контракт связей (инварианты — держим всегда)
- **I1** stage↔transition: любая смена стадии ⇒ ровно одна строка StageTransition.
- **I2** booking↔stage: активная бронь ⟺ стадия ∈ {on_call,tz_approved,proposal,prepayment,in_work}.
- **I3** stage↔task: активная стадия, требующая шага и не ведомая ботом ⇒ ≥1 живая задача/план.
- **I4** takeover⊻bot: operator_takeover=True ⇒ wa_autonomous=False ∧ нудж выкл ∧ нет pending bot-задач. ✅ СДЕЛАНО (Шаг 1).
- **I5** delivery-by-channel: отправка строго по каналу лида. ✅ СДЕЛАНО (Шаг 0).
- **I6** failed⟹visible: failed/cancelled задачи видны в «Доставка не удалась»/«Затык». ✅ частично (Шаг 0 — failed виден).
- **I7** single-booking-per-thread: бронь на conversation_id, не на Customer (мультиканал не затирает).
- **I8** time: у Customer есть tz; брони/нуджи в tz лида в рабочие часы.

## 3. Реальные баги (проверено по коду; ✅ = починено)
- ✅ **I5 транспорт:** `run_due_followups`/`run_due_call_reminders` слали ВСЁ через Telegram →
  WhatsApp/IG-дожимы падали (failed) → тихая потеря лида. (Шаг 0)
- ✅ **I6 failed невидим:** `task_board` показывал только pending/processing. (Шаг 0)
- ✅ **I4 перехват не каскадит:** бот дожимал взятого оператором лида. (Шаг 1)
- ⏳ **booked_call_at — одно поле на Customer** → мультиканал затирает бронь, календарь гадает. (Шаг 4)
- ⏳ **decide_on_silence авто-проигрывает только in_dialog** → молчуны на qualified/proposal висят. (Шаг 6)
- ⏳ **Нет колонки tz/рабочих часов** → даты в UTC. (Шаг 4)
- ⏳ **Два движка воронки** (funnel-dispatch vs brain._FORWARD) — латентно (в проде активен один: WA_BRAIN выкл). (Шаг 3)
- ⏳ **next_action не в hot-path** (только по кнопке) → намерение не материализуется в задачу. (Шаг 5)
- ⏳ **Корень исчерпания пула** (из-за него WA_BRAIN выкл) — предусловие hot-path. (Шаг 2)
- ℹ️ **crm_enabled связывает воронку/крон.** ПРОВЕРЕНО: в ПРОДЕ `crm_enabled=ON` (крон+crm_queue
  стартуют, sweep идёт) → оркестрация НЕ выключена; агенты преувеличили из дефолта. Развязка —
  чистота кода, НЕ срочно. (отложено)

## 4. Фазы (статус)
- **Шаг 0** ✅ роутер транспорта + видимость failed. (коммит 0ae50fc)
- **Шаг 1 · I4** ✅ каскад перехвата (бот замолкает на взятом лиде). (коммит 8374e34)
- **Шаг 2** ◐ корень пула. ПЕРЕОЦЕНКА: пул НЕ узкое место при текущем масштабе (WA-инбаунд ограничен ≤3 `_WA_INBOUND_SEMA`, brain ≤2, пул=50 → запас огромен; band-aid 20/30+fail-fast работает; WA_BRAIN выкл скорее из-за невалидированных решений brain, чем из-за пула). Поэтому СДЕЛАНА ОСТОРОЖНАЯ версия (`_HOTPATH_SEMA=15` потолок параллелизма горячего пути, НЕ трогаем транзакции) ✅ коммит cd35a1f — структурно исключает исчерпание пула под всплеском website/telegram + делает безопасным будущее авто-ведение. ПОЛНАЯ версия (release-коннект-во-время-LLM, restructure _handle_message) ОТЛОЖЕНА как прод-рискованная и НЕ срочная — делать вместе с владельцем когда понадобится масштаб.
- **Шаг 3** ⏳ StageMachine (единый писатель стадии, всегда StageTransition, удалить _FORWARD); decide_on_silence на все активные стадии.
- **Шаг 4** ⏳ бронь → call_booking(conversation_id) dual-write (тронуть ВСЕ ~6 читателей разом) + колонка tz + рабочие часы; sticky-primary диалог.
- **Шаг 5** ⏳ единый LeadPlan на сообщение (под apply_plan + row-lock + дебаунс; guards.py; пороги консервативны); копилот-карточка + plan_feedback + обучение.
- **Шаг 6** ⏳ diagnostics→supervisor с инвариантами I1/I3/I4/I5/I6/I7/I8 + синхронный guard; молчун→каденция→lost→revive (настраиваемо); серверные фильтры/виды по статусам.
- Каждый шаг — за отдельным флагом с откатом.

## 5. Открытые вопросы (для будущих фаз)
- Источник tz лида без телефона (website/@lid): спрашивать в диалоге / дефолт тенанта / по IP.
- Окно дебаунса сообщений (3–5с / N сообщений) — калибровать на трафике WAHA.
- Sticky-primary порядок при конфликте: бронь > takeover > прогресс воронки (подтвердить).
- Пороги llama (self-confidence не калиброван) — детерминированные стражи на критичные намерения.
